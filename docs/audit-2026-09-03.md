# Security audit, 2026-09-03

Scope: `contracts/src/` as deployed on Base mainnet, plus the key handling around them.
Method: threat model first, then tools, then reasoning, then an exploit path per finding.
Tools run: gitleaks (history), semgrep. slither and aderyn are not installed on this machine.

## Where the keys live, before any Solidity

| Key | Location | Can do | Hot? |
|---|---|---|---|
| Owner EOA | `contracts/.env`, and pasted in a chat transcript | everything, including `ownerCall` to drain the account | yes |
| Session key | `contracts/.env` (stands in for the enclave until step 5) | only what the fence allows | yes |
| Passkey | not yet registered | co-sign above the threshold | n/a |

**The fence bounds the agent, not the operator.** Anyone with this machine has the owner key and
can empty the account regardless of any check in these contracts. That is acceptable only because
the account holds about five dollars. It stops being acceptable the moment it does not.

There is no upgrade path and no admin key beyond the owner: the contracts are immutable.

## Findings

### 1. Anyone could exhaust an account's daily budget. High. FIXED.

`VoicePolicy.validateUserOp` accepted a call from any address. The EntryPoint is what binds a user
operation to its hash; a direct caller binds nothing. So an attacker could take one `(opHash,
signature)` pair observed on chain, pair it with fabricated order fields up to the per-trade cap,
call the policy directly, and have `_recordSpend` fire. Repeat until the daily cap is gone. No keys,
no funds moved, cost of gas only, and the account cannot trade for the rest of the day.

Proved in `test/Griefing.t.sol`, which now stands as the regression test.

Fix: refuse any caller that is not `op.sender`.

### 2. A failed execution still spends the daily budget. Medium. Not fixed.

`_recordSpend` runs during validation, before the call happens. If `placeOrder` reverts, the
EntryPoint records the operation as executed-and-failed and the budget is gone anyway. An agent
looping on a failing order burns the day.

This is inherent to enforcing a cap inside a validator, and the alternative is a post-execution
hook the account would have to be trusted to call. Left as designed, recorded here rather than
discovered later.

Related: writing storage during validation breaks the ERC-4337 validation storage rules, so **this
account cannot be submitted through a public bundler.** The operator self-bundles, which is why it
works. Anyone reusing this module elsewhere needs to know that.

### 3. The passkey challenge is matched by substring. Medium. Not fixed.

`WebAuthn._challengeMatches` searches `clientDataJSON` for `"challenge":"<base64url>"` as a
substring rather than parsing the field. A `clientDataJSON` whose `origin` contains that text would
pass while the authenticator actually signed a different challenge.

Exploiting it needs a signing capability on the same rpId, which means script execution on our own
origin. Narrow, but the fix is cheap and the current code makes a claim it does not quite earn.

Fix: parse the JSON object and compare the `challenge` field itself.

### 4. `attestationHash` is stored and never checked. Medium as a claim, none as an exploit.

The design says the validator refuses an operation whose session key belongs to an image the owner
did not approve. The deployed contract stores the hash at registration and never reads it again.

There is no cheap way to verify a TDX quote on chain, so this field can only ever be a record of
what the owner believed, not a check. Section 8 of the spec shows a comparison that cannot exist.
Either the spec is corrected or the field is removed; leaving both is the bad option.

### 5. `execute` is callable by the owner as well as the EntryPoint. Low.

`ownerCall` already gives the owner arbitrary calls, so the owner branch in `execute` is a second
unfenced path that buys nothing. Narrowing `execute` to the EntryPoint alone would reduce the
surface without losing anything.

### 6. The daily window resets rather than slides. Informational.

Spending the cap just before a window boundary and again just after gives twice the cap in a short
period. Standard for this pattern, and the per-trade cap still bounds each individual order.

## What was checked and found clean

Reentrancy on `execute` (a re-entering target is neither the EntryPoint nor the owner). Signature
replay across chains and operations (the EntryPoint's hash covers chain id, EntryPoint address and
nonce). `ecrecover` returning `address(0)` (rejected explicitly). Signature malleability (upper-half
`s` rejected, with a test). P256 verification failing open when the precompile is absent (returns
false, with a test). Arithmetic (0.8 checked, no unchecked blocks). Committed secrets (none in
history; the two gitleaks hits are the EIP-712 domain separator and order type hash).
